# Self-hosting Falconia

Everything runs in Docker on one machine. You need **two hostnames**.

## Why two hostnames

One serves the application, the other serves artifacts. They must be different
origins, and this is not a recommendation: the backend checks it at startup and
refuses to start if they are the same.

An artifact is code generated by a model and reviewed by nobody. If it ran on
the application's origin it could read the session token of whoever is looking
at it, call the API on their behalf and delete their work. Served from another
hostname it can do none of that, even if someone one day removed the iframe's
`sandbox` attribute to make something work.

```
                       ┌── falconia.example.com ─────────────┐
Internet ── TLS ── proxy                                      ├── falconia-frontend (nginx)
                       └── usercontent.falconia.example.com ─┘          │
                                                                        │  /api, /mcp
                                                              falconia-backend :8080
                                                              falconia-backend :8081  (content)
                                                                        │
                                                              falconia-postgres :5432
```

No container publishes a public port. Backend and database sit on an internal
network the proxy cannot reach.

> Tip: use a hostname for content that is not a subdomain your app sets cookies
> on. A separate registrable domain (`falconia-usercontent.com`) is even better
> than a subdomain, though a subdomain is already a separate origin.

## Steps

```bash
git clone https://github.com/clackes/falconia /opt/falconia
cd /opt/falconia
cp .env.prod.example .env.prod
chmod 600 .env.prod
$EDITOR .env.prod
```

The values to set:

```bash
APP_BASE_URL=https://falconia.example.com
CONTENT_BASE_URL=https://usercontent.falconia.example.com   # different from the first
API_BASE_URL=https://falconia.example.com

JWT_SECRET=$(openssl rand -hex 32)
CONTENT_SECRET=$(openssl rand -hex 32)                      # another, different one

ALLOW_REGISTRATION=false
```

`ALLOW_REGISTRATION=false` closes sign-up, but the first account can still be
created while the instance is empty: without that exception there would be no
way to get a first administrator.

Create the proxy network if it does not exist, then start:

```bash
docker network create proxy   # or set PROXY_NETWORK to your proxy's network
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

The first account to sign up becomes the administrator. From there, create a
team and invite people by email.

## The reverse proxy

Send both hostnames to `falconia-frontend:80`. The nginx container tells them
apart by itself: the content block answers hostnames starting with
`artifacts.`, `content.` or `usercontent.`. If you pick different names, adapt
`server_name` in `frontend/nginx.conf`.

**Caddy**

```
falconia.example.com, usercontent.falconia.example.com {
    reverse_proxy falconia-frontend:80
}
```

**Cloudflare Tunnel** (remotely managed): add two public hostnames in
*Zero Trust → Networks → Tunnels → your tunnel → Public Hostname*:

- `falconia.example.com` → HTTP → `falconia-frontend:80`
- `usercontent.falconia.example.com` → HTTP → `falconia-frontend:80`

## Commands

```bash
C="docker compose --env-file .env.prod -f docker-compose.prod.yml"

$C up -d --build     # start, and also upgrade after a git pull
$C logs -f backend
$C ps
$C down              # volumes survive
```

Stamp the version shown in the admin panel and `falconia version` with
`FALCONIA_VERSION=v0.2.0` in `.env.prod`.

## Backups

Two things to save, and they must be saved together.

```bash
# The database
docker exec falconia-postgres pg_dump -U falconia falconia | gzip > backup-$(date +%F).sql.gz

# The file bytes
docker run --rm -v falconia_blob_data:/data -v "$PWD":/out alpine \
  tar czf /out/blobs-$(date +%F).tar.gz -C /data .
```

A database without its blobs gives artifacts that 404 on themselves; blobs
without the database are anonymous bytes. A restore needs both from the same
moment.

## Upgrading from "Social for Artifacts"

Falconia was previously called Social for Artifacts (CLI `sfa`). Upgrading keeps
everything working:

- the database migrates by itself at startup (migration `008_falconia`);
- old `sfa_pat_…` keys keep working, new keys start with `falconia_pat_`;
- artifacts using the `SFA` JavaScript global keep working (`Falconia` is the
  new name, `SFA` an alias);
- the CLI reads `SFA_API_URL`, `SFA_TOKEN` and `~/.sfa` if the `FALCONIA_*`
  equivalents are absent.

The Docker project and volumes were renamed. To keep your data, point the new
stack at the old volumes in `.env.prod`:

```bash
docker volume ls | grep -i sfa       # find them
POSTGRES_VOLUME=sfa_postgres_data
BLOB_VOLUME=sfa_blob_data
```

and keep `POSTGRES_USER`/`POSTGRES_DB` as they were.

## Details that cost time if you don't know them

**Container names have the `falconia-` prefix.** On a Docker network shared
with other stacks, a generic alias like `backend` can make the internal DNS
resolve someone else's container.

**`VITE_API_BASE` is a build-time value.** Vite inlines it into the bundle:
changing `APP_BASE_URL` needs `--build`, a restart is not enough.

**`proxy_buffering off` on the API routes.** `/api/chat` answers with SSE: with
buffering on, nginx accumulates the stream and delivers it all at the end.

**COEP is `credentialless`, not `require-corp`.** Artifacts come from another
origin, and `require-corp` would refuse them.

**Rotating secrets has two different effects.** Changing `JWT_SECRET`
invalidates every session and signs everyone out. Changing `CONTENT_SECRET`
only invalidates artifact content URLs already open, which regenerate on the
next reload. Shared `/p/` links are not affected by either.

**Migrations run at startup**, inside a Postgres advisory lock: two replicas
starting together do not fight over them. Nothing to run by hand.

## Disk space

Files are content-addressed: the same logo in ten versions takes space once.
When an artifact is deleted its blobs stay until someone collects them, from
the *Instance* panel.

Collection skips blobs created in the last hours: a deploy in progress has
already uploaded them but not linked them yet.

For large instances, or a stateless backend with several replicas, switch to an
S3-compatible bucket:

```bash
BLOB_BACKEND=s3
S3_ENDPOINT=minio:9000
S3_ACCESS_KEY=…
S3_SECRET_KEY=…
S3_BUCKET=falconia
```

In development there is a MinIO ready to go: `docker compose --profile s3 up -d`.
